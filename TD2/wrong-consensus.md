## 2. Faulty SQL clauses

Reference ([c02-reference.sql](sql/c02-reference.sql), 590 320):

```sql
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders AS o
JOIN product AS p ON p.product_id = o.product_id
JOIN customers AS c ON c.customer_id = o.customer_id
WHERE c.birth_date > '2000-09-25' AND c.birth_date <= '2001-09-25';
```

Both faulty queries run unchanged and without error, and return 0 ([c02-faulty-gpt-oss-20b.sql](sql/c02-faulty-gpt-oss-20b.sql), [c02-faulty-dots.sql](sql/c02-faulty-dots.sql)):

```sql
-- GPT-OSS 20B (returns 0)
SELECT COALESCE(SUM(o.quantity_product * p.price),0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE c.birth_date > '2025-09-25' AND c.birth_date <= '2026-09-25';
```

```sql
-- Dots3-Note (returns 0)
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE (
    CAST(substr(c.birth_date, 1, 4) AS INTEGER) + 25 = 2026
    AND substr(c.birth_date, 6, 2) = '09'
    AND substr(c.birth_date, 9, 2) = '25'
)
AND o.date >= '2026-09-25 00:00:00'
AND o.date < '2026-09-26 00:00:00';
```

The JOINs are correct in both queries; the error is in the `WHERE` clause.

- **Required window.** "Exactly 25 years old on 2026-09-25" means born in **]2000-09-25 ; 2001-09-25]**: the 25th birthday has passed (born on or before 2001-09-25) and the 26th has not (born after 2000-09-25).
- **GPT-OSS 20B** tests `birth_date` in ]2025-09-25 ; 2026-09-25]. The bounds have the right shape, but the model kept the reference date without subtracting 25 years, so it selects customers aged 0. Birth dates in the base range from 1958-06-08 to 2006-08-15: no customer is in that window.
- **Dots3-Note** adds two conditions the question does not ask. We ran each one alone to measure its effect:

| Clause of the Dots query | Run alone | Effect |
|---|---:|---|
| Birth date **equal to** 2001-09-25 (one day instead of a one-year window) | 135 000 | keeps only C001, misses 455 320 |
| Orders placed **on** 2026-09-25 (instead of all orders) | 0 | no order on that day (last order: 2026-09-20 19:24:25), removes the remaining 135 000 |

Files: [c02-dots-birth-clause-only.sql](sql/c02-dots-birth-clause-only.sql), [c02-dots-date-clause-only.sql](sql/c02-dots-date-clause-only.sql).

Two different mistakes, the same result: each filter selects an empty set, and `COALESCE(SUM(...), 0)` turns the empty set into 0. The models agree on the effect, not on the logic.

## 4. Independent check

- **Reference.** Section 4 of `pair_b_check.py` recomputes C02 from `customers.csv`, `orders.csv` and `product.csv`, with completed age computed in Python from the date components, without SQL. It finds the same 6 customers, the same 82 order lines and the same 590 320 cents.
- **Check that detects the shared error.** Before accepting an amount, count the population selected by the filter, independently of the model ([c02-population-check.sql](sql/c02-population-check.sql)):

| Filter | Customers | Order lines |
|---|---:|---:|
| C02 reference | 6 | 82 |
| C02 GPT-OSS 20B | 0 | 0 |
| C02 Dots3-Note | 0 | 0 |
| C06 reference (true zero) | 0 | 0 |
| C14 reference (true zero) | 0 | 0 |

A zero amount with a non-empty reference population is rejected and sent to the reference computation. Both faulty C02 queries are caught, although they agree. True zeros pass: on C06 and C14 the reference population is empty too.

## Consequence for the panel and the checking

- **A consensus is not a proof**, even across distinct families: two unrelated `WHERE` errors converge on 0, the value of any empty filter. A consensus on 0 deserves less trust than a consensus on another amount.
- **Panel choice.** The fixed 2-of-3 panel avoids this case only because it excludes 20B and Dots. The 3-of-5 quorum does not return the wrong value but abstains, so it gives no answer and the question must be escalated. A larger panel or an escalation to another model is a candidate check, not a guarantee: three models sharing the same error would win it.
- **For the routing rule (Pair C).** On age questions, an amount shown to a customer or paid out should not rely on a quorum alone; the population check or the reference computation is required.

This is one case from twenty questions and one run per model: it describes our batch, not a general error rate.

## Mechanism illustrated: DEMO-VOTE (synthetic, not an analysis case)

Constructed teaching material, not model outputs and not the shop database. Kept separate from the measured counts of our batch. One sale on `2026-01-01` for 100 cents; period 1 January inclusive to 2 January exclusive; reference 100.

| Variant | Filter | Result |
|---|---|---:|
| Two proposals | `sale_date > '2026-01-01' AND sale_date < '2026-01-02'` | 0 |
| Third proposal | `sale_date >= '2026-01-01' AND sale_date < '2026-01-02'` | 100 |

Proposals `[0, 0, 100]`, 2 of 3: `vote_k_sur_n` returns a consensus on 0 against a reference of 100. The strict `>` excludes the sale made exactly on the start bound, the same boundary mechanism as C005 and C001 above. A 3-of-5 quorum cannot be declared on this example, which has only three proposals.
